# Platforms: what the site can actually do

A recommendation the platform cannot execute is not a recommendation. It is homework
for somebody who will discover in an hour that it was impossible, and it costs more
trust than saying nothing.

Profile section 1 already records **CMS / platform**. This file is what to do with
it. Read the row for the platform before writing a fix, and where the platform
cannot do the thing, say so in the brief and name what it can do instead.

**Checked 2026-08-28.** These platforms ship changes often. Re-check before treating
a limit as current, and prefer a limit you have just verified on the actual site
over anything written here.

## The short version

| | WordPress | Webflow | Framer | Lovable |
|---|---|---|---|---|
| Server-rendered HTML | Yes | Yes | Yes, pre-rendered at publish | **Depends, see below** |
| Per-page title | Core | Page settings | Page settings | Set in code |
| Meta description | **Plugin** | Page settings | Page settings | Set in code |
| Custom canonical | **Plugin** | Global plus per page | Auto, editable per page | Set in code |
| `noindex` per page | **Plugin** | Sitemap indexing toggle | Page settings | Set in code |
| Sitemap | Core since 5.5 | Auto | Auto | Supported |
| `robots.txt` | Virtual, plugin to edit | Editable in settings | Auto | Supported |
| 301 redirects | **Plugin or server** | Site settings | Site settings | Depends on host |
| JSON-LD | **Plugin or theme** | Custom code in head | Custom code | In the page component |

Bold means the capability is not there by default and something has to be added.

## WordPress

**Ask which SEO plugin is installed before writing anything.** It is the single
question that decides what is possible, and the answer changes the instructions
completely. Yoast, Rank Math, All in One SEO, SEOPress and Slim SEO all do the job
and none of them put the fields in the same place.

- **Core gives you less than people assume.** Title tag support, if the theme
  declares it, and XML sitemaps at `/wp-sitemap.xml` since WordPress 5.5. That is
  close to the whole list. Meta descriptions, canonicals, `noindex` controls,
  Open Graph and JSON-LD all arrive with a plugin.
- **`robots.txt` is usually virtual**, generated by WordPress rather than a file on
  disk. Editing it means a plugin or a real file, and a real file wins, which is a
  common cause of "my robots.txt changes did nothing".
- **Two SEO plugins at once is a real failure mode.** Both emit canonicals and
  Open Graph, the page ends up with duplicates, and the symptom looks like a theme
  bug. Check for it before diagnosing anything subtler.
- **Redirects need a plugin or server config.** If the site is on managed hosting,
  the host may have its own redirect panel that the plugin does not know about.
- Block themes and classic themes differ in where template-level markup lives. Say
  which one the fix applies to.

## Webflow

Static hosting serving real HTML, so rendering is not a problem here. The
constraints are structural.

- **Canonical has two levels.** A global canonical in Site settings makes every page
  self-referencing automatically, and individual pages can override it. Webflow's
  own documentation warns to include the protocol and omit the trailing slash,
  because getting that wrong produces double slashes across every subpage.
- **`noindex` is a Sitemap indexing toggle** in Page settings rather than a meta
  field, which is why "I set noindex and nothing happened" usually means someone
  edited custom code instead of the toggle.
- **301 redirects are relative to the root domain and do not apply to localised
  slugs or subdirectories.** Redirecting `/old` does not redirect `/es/old`. Each
  needs its own rule, and a migration brief that assumes otherwise will leave half
  the locales broken.
- **A directory cannot mix static pages and CMS collection items.** A collection and
  a page folder cannot share a slug. This kills a lot of otherwise sensible URL
  restructures, so check it before proposing one.
- **Pagination canonicals are a known gap.** Paginated collection lists do not give
  you the canonical control you would want. Treat it as a limitation to state, not
  a defect to fix.
- JSON-LD goes in the page's custom code head area, and on collection pages it can
  take dynamic fields from the collection.

## Framer

- **Pre-rendered at publish**, so crawlers receive real HTML including the
  responsive variants. Rendering is not the problem.
- **Canonicals are automatic and self-referencing**, editable per page where a
  specific target is needed.
- **`sitemap.xml` and `robots.txt` are generated automatically.** That is convenient
  until you need something unusual in them, so check what is actually served before
  promising a change.
- Title and description live in page settings, and CMS collection pages carry their
  own SEO fields.
- JSON-LD goes in custom code.

## Lovable

The most important row in this file, because the failure mode is invisible and this
pack has hit it on a real site.

- **Rendering depends on when the app was created.** Apps created from 13 May 2026
  use TanStack Start with server-side rendering. Older apps are React plus Vite with
  **on-request pre-rendering**.
- **Pre-rendering serves verified crawlers only.** Google, Bing, social bots and AI
  engines including ChatGPT and Claude get rendered HTML. Third-party SEO scanners,
  which includes `seo.py`, get the single-page-app shell.

  **So `requires_js: true` on a Lovable site is not evidence that Googlebot sees an
  empty page.** It may only mean the pre-renderer did not recognise the fetcher.
  Confirm with a browser render or Search Console before reporting a rendering
  problem, and never put a critical rendering finding in a report on the strength of
  our fetch alone.

- **A sitemap can advertise pages the app does not have.** Routes like
  `/guide/:slug` resolve against a backend, so a URL in `sitemap.xml` whose record is
  unpublished renders the app's own 404 while still answering HTTP 200. That is a
  soft 404 at scale, it passes every robots.txt check, and the site looks fine to
  anyone clicking around the navigation.

  This pack found exactly that on a live site: 22 of 31 sitemap URLs rendered a 404
  while the guide library reported zero published entries. Check a sample of sitemap
  URLs in a browser before concluding anything about a Lovable site.

- **Only publicly published apps are indexable.** Private or unpublished projects
  and branded workspace URLs never are, so "we are not indexed" sometimes has a
  one-click answer.
- Titles, descriptions and JSON-LD are set in the page component, which means every
  change is a code change and belongs to whoever owns the repository.

## How to use this in a brief

State the platform, then write fixes it can execute:

- **Name the surface, not the outcome.** "Set the canonical in Page settings" beats
  "add a canonical tag" on Webflow, and "add it to the SEO plugin's field" beats
  either on WordPress.
- **Where the platform cannot do it, say so and offer the nearest thing.** A brief
  asking for per-page canonicals on paginated Webflow lists is asking for something
  that does not exist.
- **Say who owns the change.** On Webflow and Framer most of this is a designer in
  the editor. On Lovable all of it is a developer in the repository. That difference
  decides whether a fix takes ten minutes or a sprint.
- **Never assume the platform from the domain.** Ask, or check the served HTML.
  Guessing wrong produces confidently wrong instructions.
